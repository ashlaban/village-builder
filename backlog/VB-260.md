Goal: VB-214 built saves in the page and checked them once by hand (Kim, 10 Nov: deliver the code, test later). This task makes those checks permanent and reports the numbers and pictures VB-214's criteria asked for.
Acceptance criteria:
- [x] `tests/browser-saves.js` (now a script run by hand that prints its results) asserts, in real Chromium and in verify (`tests/run.js`):
  - save to a slot, reload the page, Load archipelago and Continue: the state's hash, the year and the played pawn match;
  - a stored save with another build id shows "Made by another build of the game; it cannot be loaded", **Delete it** removes it, and **Start a new game** generates the same archipelago;
  - **Delete archipelago** removes all of an archipelago's saves and no other's;
  - a file saved and loaded again matches the state's hash and takes no slot; a file of another build is refused with the message;
  - the page hidden (`visibilitychange`) writes the auto slot, once for one game time;
  - from a running game, Main menu then Back to game leaves the state's hash as it was;
  - no console errors.
- [x] Times reported, in Chromium and in Node (`tools/bench.js`), at small-y40 and medium-y5, each stage apart (encode, stringify, gzip, IndexedDB write; read, gunzip, parse, decode). Stale fixtures are said to be so. The 0.5 s line is VB-199's and VB-226's, not this task's.
- [x] Screenshots of the landing page, the generation screen and the Saves overlay (from the landing page and from a game), desktop and phone, in `docs/img/vb-214-*.png`.
- [ ] `design.md`'s Saving point (Commands, time steps and views) is brought up to Kim's decisions of 10 November, listed in VB-214's notes, by whoever holds the design pass; until then VB-214's notes stand.
