# VB-1405: Share work candidates and track queued verbs through explicit outcomes

Goal: Implement shared work selection and explicit completion of queued commands for the existing verb, job and player queue systems.
Acceptance criteria:
- [ ] The Actions list and autonomous matcher use the same read-only evaluation of a posted job for a pawn. Both can construct the same work command for the same pawn and job. Preserve the matcher's indexed search, ranking, tie order and timing, and the player's ability to see unavailable choices with reasons. Candidate discovery does not post jobs, mutate simulation state or draw randomness.
- [ ] Execution rechecks live state before taking a job. The dispatcher exposes three explicit results to the queue: done, refused(reason), or pending(ref). A refusal has no side effects. Existing callers of issue and Sim.command that expect true or a reason string retain that contract, including strict equality checks. Both interfaces reach the same execution path exactly once.
- [ ] The queue asks the owning verb or assignment system whether its pending reference is still active. Remove the verb-name completion switch from sim/player. For work, the reference identifies this pawn's particular assignment. Releasing it advances the queue even if another worker continues, the same job key is reposted, or the original pawn later takes a fresh assignment. Full, partial and background assignments resolve against their own slots.
- [ ] Preserve the existing queue limit, order, recheck at execution, continuation past refusals, delivery of a carried load before switching, and unqueue semantics. Preserve work interruption and the timing of walkTo, goHome and idle. Define done as completion of the command's own immediate act. Existing immediate verbs that schedule later activity can complete once the scheduling succeeds.
- [ ] Pending references are plain save data and resume after save/load without issuing a begun command twice. Exercise an older supported save with a begun entry that has no reference, including the case where its assignment has already ended. Ended assignments leave no unbounded history.
- [ ] Extend the focused command, opportunity, player queue and attention tests. Cover competing claimants between preview and execution, two pawns on one job, release and reacquisition, pending side work, refusal followed by a valid command, and save/load mid-assignment. Run npm test and npm run verify. Check matcher cost against the starting revision with the same fixture and report any change in job scans or assignment order.

## Implementation brief

Today sim/opportunities builds player-facing work rows using eligibility, fit and verb checks. sim/jobs separately searches candidates and directly issues work to the matcher’s chosen pawn. Player choices enter a FIFO in sim/player. sim/commands.issue calls the registered check and run, discards the run result, and returns true or a reason. sim/player.LASTS then infers duration from mutable pawn state. Its work predicate reads the main job even though sim/agents can also claim partial and background work.

Start with src/sim/opportunities.js (work), src/sim/jobs.js (fit and the work issuers), src/sim/commands.js (issue), src/sim/agents.js (the registered work verb, hold and release), and src/sim/player.js (LASTS, queue, playerStep and unqueue). Trace the save path and the callers of issue before changing the return contract. Existing tests/commands.js, tests/opportunities.js, tests/player.js and tests/attention.js exercise the public entry points.

Keep candidate evaluation separate from selection policy. The player chooses and the matcher ranks. Share the job-level logic at the point where each already has a candidate. Building every UI row for every simulated pawn would add work to the matcher. Preserve UI-only previews for work that has yet to be posted.

Let each domain register or supply its own completion semantics. The dispatcher stays independent of job and pawn modules. Only the queue needs to retain a pending reference, and the assignment owner remains the authority on whether it is live. A completed job and an interrupted assignment both release the queue. Other participants may still be working. Preserve full-work replacement and side-work coexistence when moving the current interruption logic out of LASTS.

Limit the patch to verbs, posted jobs, assignments and queue integration. Project selection, offer or gift lifecycles, and a player-facing workflow editor are outside this task.
