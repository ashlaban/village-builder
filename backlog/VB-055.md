# VB-055: TypeScript: real modules, typed state, a formatter and measures of width: survey and tasks
Status: ready
Priority: 3
Size: S
Arch: yardstick
Phase: implement
Design ref: none (test infrastructure)
Goal: A misspelt field (`hh.grian`), an argument in the wrong place or a holder of the wrong kind is silent in plain JavaScript until it misbehaves. Kim decided on 10 November (code review) to move the code to TypeScript, by a plan: real modules first, then `.ts` and types for the state, then strictness; and with the same sweep a standard formatter, and measures of a module's width in place of the cap on its length. Survey what the move touches and write the implement tasks. This replaces the first version of this task (`checkJs` with JSDoc and a hand-written `types.d.ts`), which sees little: every module is reached through `VB['<key>']`, which has no type, so no call between modules is checked.

## Survey (12 November 2026, checkout at `1e9b93b`; every count has its command)

The tasks it produced are in `docs/typescript-plan.md` (P1 to P14). The questions are in `QUESTIONS.md`, "VB-055: the move to TypeScript". Nothing under `src/`, `tests/` or the build changed; no dependency was installed in the repository (scratch installs of TypeScript 5.6.3, esbuild 0.25.0 and Prettier 3.3.3 were made outside it).

Tried here, on Node v22.23.4 (`node --version`; `.github/workflows/checks.yml` uses `node-version: 22` in both jobs, so the latest 22.x), in a scratch directory:
- `node b.ts` runs a file with annotations and `import { f, type P } from "./a.ts"` with no flag. An import without the extension fails (`ERR_MODULE_NOT_FOUND`). `enum`, `namespace` and constructor parameter properties fail with `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` (the last: "not supported in strip-only mode").
- `require("./a.ts")` from a `.cts` file returned the exports of a `.ts` file with `export` syntax.
- `module.stripTypeScriptTypes(src, {mode: 'strip'})` exists, warns (experimental), and keeps every position (types become spaces), so acorn parses its output with the original lines and columns.
- A module namespace is frozen: assigning to `M.bump` after `import * as M` throws `TypeError` in a `.ts` run by Node, so an export cannot be replaced, as the task says.
- esbuild 0.25.0 bundles `.ts` files into one IIFE (`--bundle --format=iife`), types removed.
- Not tried: the least Node version for type stripping without a flag (from memory 22.18; to verify in P8), Node 20, `require()` of `.js` files written as ES modules, a bundler over the real modules, Prettier's or tsc's behaviour on the real `.ts` files.

### The modules and what each import and export becomes
- `src/manifest.json`: 63 modules (`node -e` on the file): `vb`, 5 in `gen/`, `gen`, `culture`, 54 in `sim/` (`ls src/sim | wc -l`), `sim`. 11,980 lines (`wc -l`); 3 over 400 lines: `gen` 548, `sim/relations` 401, `sim/heirs` 401. Each registers as `VB['key'] = (() => { ...; return {...}; })()` and reads others with `const {a, b} = VB['x']` at its top; the manifest's order is the only order.
- Imports: `tools/writes.js`' `build()` finds 416 imports at load and 75 lookups inside functions; `grep -rohE "VB\['[a-z/]+'\]" src | wc -l` gives 506 references in the modules (the counts differ because one import reads several names).
- Becomes: `import { a, b } from './x.ts'` for the first, `export` on each name of the `return` list for the second. `sim.js` is the facade over the others (106 exports). The page reads `Sim` (252 uses) and has 64 matches of `\bVB\b` (some are task ids such as `VB-341` in comments: how many are the object is not checked).
- `src/load.js` (requires the manifest in order and returns `globalThis.VB`): 120 tests and tools load through it (`grep -lE "src/load|/load(\.js)?'"`); the task text said 96, a recount gives 120; 137 files mention `VB[` or `globalThis.VB`. Keeping `load.js` as the one place that builds `VB` leaves them unchanged: the plan's choice (P3, P6).

### The late lookups
- The task says 16. Counted: 17 calls of `later('...')`, all in `sim/commands.js` (`grep -rn "later(" src`), on nine modules (lifecycle 5, heirs 2, settle 2, occasions 2, farmclaims 2, service, membership, cottage, clock 1 each); plus four one-line shims `const issue = (st, cmd) => VB['sim/commands'].issue(st, cmd)` in `sim/relations`, `sim/help`, `sim/expansion`, `sim/farmclaims`. `tools/writes.js` counts 19 late lookups and 19 cycles; `node tools/dependencies.js` prints 20 upward edges of 500.
- Each is a cycle that stays: `tests/dependencies.js` asserts that every cycle passes through `sim/commands`, command dispatch, the one upward door (VB-230; `docs/architecture/target-v2.md`, 3.2). ES modules allow a cycle when no module uses the cyclic import at load; these lookups are used inside functions only (that is why they are late), so they become plain imports (P6). None is to untie. To watch: uses at load, such as `KINDS.dig = VB['sim/dig'].KIND` in `sim/kinds.js:376`, depend on evaluation order; P5 lists them.

### Tests and tools that replace a module's function
- The task says about 22 files. Found by listing every assignment to a module member in `tests/`, `tests/lib/` and `tools/` (a regex for assignments with a function on the right, then reading the hits): 10 files wrap or replace a function or a table entry of a module: `tools/perf.js` (the `SYSTEMS` table: 25 functions in 12 modules), `tools/moving-profile.js`, `tools/route-bench.js` (`refreshRoutes`), `tools/wood.js` (`fellTree`, `clearTile`), `tests/spread.js` (`settlementStep`, `roundPhase`), `tests/plans.js` (`R.value`), `tests/lib/owner-caches.js` (`refreshRoles`), `tests/lib/line.js` (each verb's `run`: a data table, which stays assignable), `tests/lib/record.js` (a state field, not a module function) and `tests/bench.js` (`fixtures.loadFixture`, a test library's function). Seven read `src/manifest.json` to require each module and wrap after it registers: `tools/perf.js`, `tools/moving-profile.js`, `tools/route-bench.js`, `tools/wood.js`, `tools/stocks.js`, `tests/spread.js`, `tests/lib/owner-caches.js`. The "about 22" may count files that set a constant table (`CLAIMS.outPerFarm`, `GOODWILL.halfLife`, `SOCIAL.seek`, `ROUTE.cacheMax`, `FIELDS.room`, `SLOPE.perRise`: 8 files), which an export does not prevent, the table being an object; not rechecked.
- One hook, chosen in P3: the build's own instrumenting (an esbuild plugin that wraps the named exports in a bundle made for the tool). Why: `tools/perf.js` is built on "nothing is added to `src/`"; production code pays nothing; the one place a tool changes is the loader. Against it: the plugin must rewrite exports, and is not prototyped (P3's first step). The fallback is a registry in the source (`probe(key, name, fn)`, an identity unless a hook is installed before load). A Node module-customisation hook was not chosen: it acts on the module graph, not on a binding (behaviour not tried here).
- A property of today's wrapper to keep or to state: it wraps right after a module registers, so only modules loaded after it see the wrapper; a call inside the module itself is not timed. P3 says which the bundled version does.
