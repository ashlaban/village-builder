# VB-1616: Agent workflow: adaptive context resets at task boundaries, beside the 120-call ceiling
Status: done (2026-11-24)
Priority: 3
Size: M
Design ref: `.claude/agents/vb-task.md`, step 8 (the ceiling and the handover); `docs/agents/worker.md`, section 1.3 (a task that reports `continue`); `docs/review-agent-workflow.md`, sections 2 and 8, and VB-1615's section 10 (the estimate); `tools/inbox.js` (`CEILING`, `result`, `calls`); `AGENTS.md`, Taking a task, step 5 and Spending turns
Goal: An agent whose context has grown past a threshold T hands the rest of its task to a fresh context at a cognitive boundary (the investigation done, or a coherent phase committed with tests green), or when it is stuck. It does so through the existing continuation, with a structured handover that carries what the next context needs and nothing else: verified facts, hypotheses, rejected hypotheses, decisions and their reasons, invariants, the criteria left, commands and source locations. The 120-call ceiling stays as the safety net, unchanged. The reset is enabled as a logged change, which starts a period that VB-1615's tools compare with the period before. It is then kept, adjusted or abandoned by the rules under Evaluation. A smaller context is not, by itself, evidence of better work.
Acceptance criteria:
- [x] A handover template, `docs/agents/handover.md`, read only when handing over and not loaded by every sub-agent. Its sections:
  - **Verified**: each fact with the command or `file:line` that shows it;
  - **Unverified**: hypotheses and conclusions not checked;
  - **Rejected**: each hypothesis, with what ruled it out;
  - **Decisions**: each with its reason;
  - **Invariants**: those that bind the rest of the work;
  - **Criteria left**;
  - **Commands**: to reproduce and to test;
  - **Places**: file, function and line;
  - **Not carried**: assumptions now obsolete, which the next context should not make.

  At most 60 lines or 4 KB, with no transcript excerpts and no file contents beyond a quoted line. The ceiling's continuation (step 8 of `vb-task.md`) uses the same template. `tests/context-size.js` shows `vb-task.md` and `AGENTS.md` grown by no more than three lines between them.
- [x] The handover is stored, not relayed: `node tools/inbox.js note ID handover --body -` (a new kind), and `node tools/inbox.js handover ID` prints the latest. The continuing prompt names the command, so the orchestrator's context grows by a line, not by the handover. A single-task session hands over the same way: it starts a fresh `vb-task` sub-agent with that pointer and waits for its result, doing no more exploring itself.
- [x] `node tools/inbox.js result ID status=continue reason=ceiling|boundary|stuck`. A voluntary reset (`boundary`, `stuck`) is refused below context T (the value VB-1615's estimate proposes), before a run's 30th call, or with no new commit since the run started. A task gets at most one voluntary reset in this first period, besides the two continuations at the ceiling. A second `stuck` in a task ends it `needs-review`. `CEILING`, `WARN` and `CONTINUATIONS` stay as they are.
- [x] `node tools/inbox.js calls` prints, once the context passes T, that the next boundary is the place to hand over. It prints a stuck hint once VB-1615's failure streak or repeats reach 3. It never ends a run itself.
- [x] `vb-task.md` step 8 and `AGENTS.md` (Taking a task) say the above in at most three lines between them. A run that stays below T is not split into phases.
- [x] Each run records the reset's reason, the handover's bytes, the reconstruction (the continuing run's calls and context before its first edit), and the orchestrator's calls spent on each continuation. VB-1615's period comparison shows them.

Method: the reset triggers considered, and what is done with each.
| Trigger | How it is detected | Used as |
|---------|--------------------|---------|
| Context size (estimated tokens) | mechanically, from the transcript's usage (`inbox.js calls`) | the gate: no voluntary reset below T |
| Investigation done, before the first edit | the agent's judgement; checkable (nothing under `src/` edited yet, the plan written in the handover) | a boundary |
| A coherent implementation phase done | the agent's judgement; checkable (a commit, `npm test` green) | a boundary |
| Repeated failures, or the same thing investigated again | a heuristic (VB-1615's failure streak and repeats); false positives when a test is legitimately rerun | a hint from `calls`; reset as `stuck`, by judgement |
| A change in the understanding of the problem | judgement only; not detectable | not a trigger: the handover's Not carried section |
| Model calls (120) | mechanically | unchanged: the hard ceiling |
- Costs a reset adds, all of them measured: a fresh boot (17k to 20k tokens of context for a sub-agent), the handover written and read, the calls spent reading again before the first edit, the cache written for the new context, and the orchestrator's calls. The estimate (VB-1615, section 10) says where these are repaid; below T they are not, so short tasks are left alone.
Evaluation: the comparison, made with VB-1615's period tools.
- Population: the tasks with a run whose context reached T ("eligible"), in both periods, stratified by size, model and run kind. The other tasks are checked for no change, since the intervention should not touch them. Eligibility is decided by context reached, the same rule in both periods, never by the outcome.
- Sample: at least 15 done eligible tasks in each period, or 4 weeks after enabling, whichever comes later. With fewer, report what there is and wait.
- Computational efficiency: weighted cost per done eligible task, summed over its runs; input, output, cache-write and cache-read tokens; calls; active minutes; repeated reads; and the overhead (handover bytes, reconstruction tokens, the orchestrator's calls).
- Implementation quality: done at the first attempt (not `needs-review`); criteria ticked; merges undone for a red check; PR check failures traced to the task; reopened within 7 days (VB-1615's proxy); failure streaks of tests.
- Each is reported with its median, quartiles and n by period and stratum, kept apart: a claim about quality rests on the quality measures only.
- Retain: the eligible tasks' median weighted cost falls by 10% or more, the cost of a done task over all tasks does not rise, and no quality measure gets worse beyond the spread between periods (the done share does not fall by more than 0.1; no more merges undone or reopened tasks per task). Or quality is clearly better at the same cost.
- Adjust, once, as a new logged period: if cost is within ±10% and the overhead is more than half the saving, raise T or shorten the handover. If the resets are mostly `stuck` and those tasks fare better, keep `stuck` and drop `boundary`, or the reverse.
- Abandon: if the eligible tasks' cost rises by more than 5%, any quality measure gets worse, the period sees fewer than 5 voluntary resets (the reset is inert), or a task resets twice without a new criterion ticked. Abandoning reverts the lines in `vb-task.md`, `AGENTS.md` and `inbox.js`, and a row in the log ends the period.
