# VB-279: Refactor: the heir cache's end: roundHeirs, its watch and its family memo gone
Status: done (2026-11-15)
Priority: 2
Size: S
Arch: between
Phase: implement
Design ref: none (code structure). Survey and measurements: `backlog/VB-242.md`.
Goal: `heirRanking` (`src/sim/heirs.js:20-90`) has seven parameters, and two of them serve only the round's cache, `roundHeirs` (`heirs.js:103-147`). `watch` records which rankings depend on which pawns and spouses. `family` reuses a household's line while `hh.members` is the same array of the same length, which leans on how `moveTo` replaces one array and appends to the other. After VB-277 the marriages rank afresh in each village's step; the view is still built by the round's demand phase (`countDemand(st, roundHeirs(st).rank)`, `lifecycle.js:149`), by an offer's close for its handover (`closeOffer`, `lifecycle.js:320`), and by `matchRules` (`src/sim/matching.js:7`, `:33`) unless VB-277 has made it rank afresh; `matchRules` also serves the player's wish (`matchBar`, VB-274) and its options (`sim/opportunities`). Remove the cache.
Acceptance criteria:
- [x] `roundHeirs` and its `invalidate` go, with heirRanking's `watch` and `family` parameters and the code that serves them (`heirs.js:32-36`, `60-62`, and the `watch` call in the filter). The demand phase calls `countDemand(st)`, which ranks through its own `ownFirstOf(st)`, as the scenarios and the drawer do. `matchRules` (and with it `matchBar` and `sim/opportunities`) and `closeOffer`'s handover no longer read the view; `tests/wishes.js` and `tests/offers.js` pass.
- [x] Two parameters stay, and the PR says why. `nested` is the direct-heirs-only ranking that `ownFirstOf` needs for the rule "an heir to their own parents' farm" (`heirs.js:73-89`); it is a rule, not a cache. `ownFirstSet` is the whole-island view of first direct heirs that a pass computes once while nothing changes (`countDemand`, `firstHeirs`, `placeIfMarried`, `refreshInterests` until VB-278). It has no dependencies to track, and `tests/lib/heir-rankings.js` (VB-224) checks the candidate-lines shortcut against it. Measured by VB-242, ranking every household without it costs 2.6 to 4.3 ms at `medium-ref` (574 rankings) against 5.5 to 19 ms with it (422), and 16 to 23 against 12 to 27 ms at `small-y40` (1,109 against 338), so it saves nothing worth a parameter. It is kept only as the test's reference and a pass's shortcut. `heirRanking(st, hh, cust, nested, ownFirstSet)`: five parameters, not seven.
- [x] `countDemand`'s `rank` parameter and `placeIfMarried`'s, and their callers' plumbing, go if nothing passes them after VB-277. Otherwise the PR names who still does.
- [x] Tests: the cache comparison in `tests/marriage.js` (lines 90 to 125 at `fd74348`: the view against fresh rankings across commands) goes with the cache. `tests/counters.js` keeps `roundRank`, now the rankings of the round's day; `tools/moving-profile.js` and the rest of `tests/marriage.js` (today the only places outside `src/` that name `roundHeirs`; `tests/heirs.js` and `tests/fixtures.js` no longer do) are brought in line.
- [x] Refactor rules of `BACKLOG.md`: behaviour unchanged (`node tools/same.js --base REF` prints `same`), and the hard checks pass. `tests/counters.json` is re-recorded only if `heirRank` or `roundRank` move, which happens only if the demand phase now ranks a different number of times, and the PR lists them.
- [x] Cost (target): the demand step at `medium-ref` and `small-y40` within 60 ms. `countDemand` without the view took 5 to 13 ms (VB-242).
- [x] The PR says what fell: lines, two parameters, and the dependency on the record's events naming every household a command changed.
