# VB-241: Refactor: the calendar, one ordered table of what runs each step, hour, day, season and year
Status: ready
Priority: 3
Size: M
Design ref: none (code structure). `docs/architecture/target-v2.md`, section 3.3 (The calendar). Kim, 10 Nov 2026 (code review).
Goal: `onHour`, `endOfDay` and `advance` (`src/sim/clock.js`) call each system in a fixed order, and each system then tests the date for itself (`c.doy === HERD.springDay`, `c.season === 2 && c.sday === SEASON_DAYS - 1`, `c.sday === 0`), as the clock does for the moving round and the meetings' stages. The order decides outcomes and is written nowhere. Target-v2 (3.3) asks for one declared schedule; Kim asked on 10 November that it be formal: entries by step, hour, day, season or year, or at a named time.
Acceptance criteria:
- [ ] `sim/clock` holds one table, `CALENDAR`, in the order things run. An entry: `{every: 'step' | 'hour' | 'day' | 'season' | 'year', at: {season?, sday?, doy?, hour?, tick?} (the place within that cadence; absent: every time), when?: (st, c) => boolean (a guard that is not a date, such as `st.cenv`), owner: '<module>', run: (st, c) => void, note: '<what it is, in a few words>'}`. It is code, never saved; it is frozen with the rules registry's seal.
- [ ] `advance`, `onHour`, `endOfDay` and `newYear` become one loop over the table for what the step reached. Every date test that decides whether a system's yearly, seasonal or daily work runs moves from its module into its entry's `at`: the moving round (`clock.js:28`), the meetings' stages (`clock.js:96-100`, one entry a stage, by `tick`), spring in `sim/herds` (`herds.js:166`), the autumn count (`byre.js:181`), the season's last day in `sim/fields` and `sim/meadows` (`fields.js:145`, `meadows.js:121-122`), `fadeRelations` (`lifecycle.js:285`), `Stores.prune`. A date test that is a condition of the work itself, not of when it runs, stays where it is (the sowing window, the hay days, a job's urgency): list in the PR which were moved and which were left, and why.
- [ ] Work spread over pawns by `(day + id) % period` (`relations.js:72-73`) stays in its module: it is one daily entry. Things due at a time for one thing (a queue in `st`, Rules for cost, 4) are not built here: none is needed yet.
- [ ] `node tools/sim.js --report calendar` (or `tools/rules.js`) prints the table: cadence, place, owner, note, in order. `docs/architecture/modules.md` and `ownership.md` (section 1, the rules `sim/clock` holds) follow; target-v2 3.3 gets a line that the table exists.
- [ ] A test in `npm test` holds the table's order against a recorded list (an intended change of order re-records it and says so in the PR), and that every entry's owner is a module of the manifest.
- [ ] Refactor rules of `BACKLOG.md`: behaviour unchanged, `tests/golden.json` and `tests/counters.json` unchanged, `npm run verify` passes. `node tools/bench.js`: simulation ms a day and the longest step no higher than before beyond the runs' spread (the loop over the table must not allocate a step).
- [ ] The PR says what fell: date tests outside the clock, and lines.
