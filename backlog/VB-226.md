# VB-226: Save within 0.5 s of main thread at medium-ref, after the folds
Status: done (2026-11-10)
Priority: 2
Size: M
Arch: yardstick
Phase: implement
Design ref: Balance loops and targets (Performance budget). docs/roadmap.md, sections 5.2 and 5.3 (rule 8); docs/bench/closure.md (VB-203).
Goal: Kim's save line (9 November, VB-203): under 0.5 s of the page's main thread at `medium-ref`, counting encode and stringify; gzip may run in a worker and is reported beside it. On 9 November at `9f130e6` the save blocks the main thread 1.51 s at `medium-ref` (encode 0.95, stringify 0.56; 39.3 MB of JSON; gzip 0.58 s more), three times the line. Of the state's 36.8 MB: the households' ledgers 10.6 (VB-204 folds the routine 95% of their entries), the pawns 14.5 (their copied events 5.3, which VB-199 makes indexes; ancestry 1.4; attitudes 1.4), the record 7.9 (VB-199 folds the routine kinds), the path cache 1.2. By size alone the two folds should leave about 17 MB and about 0.65 s. Measure what is left once they land, and cut it to the line.
Acceptance criteria:

- [x] Cut the largest parts, by rule 8 (bound history) and by not saving what can be rebuilt: a cache rebuilt at load (the path cache, for example) is left out only if load stays under 0.5 s. - [x] Encode + stringify under 0.5 s at `medium-ref` (`tools/bench.js`, the median of three runs), and parse + load still under 0.5 s; the MB before and after.
- [x] The page's save compresses off the main thread (a worker or `CompressionStream`); if VB-214 has not done so, this task does.

## Implementation, 10 November 2026
Impact note: only the save's encoding changes (`src/sim/saves.js`, the codec); the live state's shape, the simulation and the golden file do
not. It reads every field of the state, as before, and writes none; no new coupling. `tests/lib/fixtures.js` reads a fixture of an older
format the build still reads, as stale (so the format-1 fixtures stay usable until the nightly workflow remakes them).

- Measured first (below): after VB-199 and VB-204 the encode, not the stringify, was most of the save, and it followed the number of
  objects walked, not the bytes. `pawn.rel` (relationship records, `{mem: {kind: {v, t}}, band}` in a Map per pawn: 48,820 records,
  101,566 memories at `medium-ref`) was 200,000 of the 306,000 objects the save walked, and 0.16 of its 0.46 s.
- Format 2 (`FORMAT = 2`, `READS = [1, 2]`: format-1 saves and fixtures still load):
  - what JSON writes as it is (a plain object or array, not shared, of strings, booleans, null, finite numbers other than -0 and such
    objects, no key starting with `$`) is returned as it is, not copied: the save shares those parts with the state, so it is written out
    before the state changes (the page and every tool stringify it at once). Only the path to an odd value is copied.
  - a Map is `{"$kv": [k, v, k, v, ...]}`, not `{"$map": [[k, v], ...]}` (`$map` is still read);
  - a pack hook: `encode(root, stop, pack)` writes an object listed in `pack` as `{"$as": name, "v": data}`, and `decode(data, revive)` makes
    it again; `save` packs each pawn's `rel` into one flat array `[other, band, n, kind, v, t, ...]` (`packRel`, `unpackRel`). Packed
    objects start at -1 in the walk's counts, so neither pass looks them up.
  - the path for an error message is kept as (kind, key) pairs and spelled out only on an error (it was a template string per value), and a
    primitive is written without a call.
- Not cut: the path cache (1.3 MB, about 20 ms): a route taken from the cache can differ from one searched afresh (the way back reversed, ties),
  so leaving it out would change the run after a load (`tests/saves.js`); the record (3.7 MB, about 30 ms) is history the game shows.
- The page's save already compresses off the main thread: `src/page/saves.js` pipes the JSON through `CompressionStream('gzip')` (VB-214);
  only encode and stringify run on it.
