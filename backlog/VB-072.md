# VB-072: Random streams per system, with saveable state
Status: done (2026-11-02)
Priority: 2
Size: M
Arch: core
Phase: implement
Design ref: none (determinism and saves); REVIEW.md, Development, debugging and inspection.
Goal: One random function, `st.rand`, feeds job matching, weather, births, deaths, fences and attitude drift. A change to one system reshuffles all the others, so a tuning comparison mixes the change with noise, and the closure's state cannot be saved.
Acceptance criteria:
- [x] A module `src/sim/rng.js` (`@sys sim/rng`) makes a random stream as plain data plus functions: `makeStream(seed, name)` returns `{ s }` (a 32-bit state, mulberry32 as today), and `next(stream)` returns a number in [0, 1) and advances `s`. A stream copied with `JSON.parse(JSON.stringify(...))` continues identically.
- [x] `st.rng` holds one stream per system: `work` (matching, idling, walking offsets), `fields` (yields), `weather`, `fences`, `births`, `deaths`, `culture` (drift, entrepreneurs), `people` (names and looks of the newborn), `society` (marriage match). Each is seeded from the scenario's seed and its name. `@state` documented.
- [x] Seeding a scenario keeps its current single stream, so the `*/seed` and `world/*` entries of `tests/golden.json` are unchanged; the yearly entries change, which is intended. Re-record and list the changed entries in the PR.
- [x] `st.rand` goes; every call site names its stream. `Culture.dailyStep`, `entrepreneurs` and `seedAttitude` take a function as today, built from the stream.
- [x] A test: advance a founders run 1 year, draw 1,000 extra numbers from `st.rng.work`, and check that the `births` and `deaths` streams return the same next values as in a run without the extra draws.
- Kim, 2 Nov 2026: every system gets its own stream (the general rule); so besides the nine above, `talk` (contacts and talk, `sim/relations`), `herds` (`sim/herds`, `sim/byre`) and `settle` (moving to new land, `sim/settle`). Tests that make every chance come up set `fix: 0` on a stream (`next` returns it while set) instead of replacing `st.rand`. The seed entries of the golden file gain one key, `rng`; their other keys stay unchanged.
- Batch A (2 Nov 2026): `src/sim/rng.js` (`next`, `fromState`, `makeStream`, `drawer`); the scenarios and `tests/lib/tiny.js` seed through a plain-data stream that gives mulberry32's sequence, kept as `st.rng.seed`, and `st.rand` draws from it. Behaviour unchanged: the golden file differs only by the new key `rng` in its 16 scenario entries (re-recorded); `npm run verify` passes.
- Batch B1 (2 Nov 2026): every call site draws from `st.rng.<system>`; `st.rand` is gone; Culture, `person()` and the name generators get `drawer(stream)`. Behaviour unchanged (golden: only `rng` changed). The stub states of `tests/deaths.js`, `health.js` and `hunger.js` carry a `deaths` stream (mulberry32) in place of their own generator (an LCG); their assertions hold.
- Batch B2 (2 Nov 2026): `splitStreams(st, seed)` at the end of each scenario's seeding and in `tests/lib/tiny.js` gives each of the 12 systems `makeStream(seed, name)`; `tests/rng.js` (in `npm test`) checks mulberry32's sequence, JSON copies, `fix`, and that 1,000 extra draws on `work` leave `births` and `deaths` unchanged; `checkState` checks one unshared 32-bit stream per system and no `fix` left set.
- Golden file: `world/*`, `calibrate` and `apiKeys` unchanged; the 4 `*/seed` entries differ only in `rng`; every key of the 12 `*/year1..3` entries that depends on draws changed (pawns, households, herds, jobs, events, cenv, talks, weather and the rest), as intended.
