# VB-177: Refactor: a pawn's movement only through `sim/agents`
Status: done
Priority: 2
Size: S
Arch: ownership
Phase: implement
Design ref: none (code structure). VB-172's map, sections 5.6 and 7.3; Kim's answer 1 of 3 November (`QUESTION_ARCHIVE.md`, "VB-172: the ownership map").
Goal: `sim/agents` writes 21 of the 26 sites of a pawn's movement; four other modules write past it. A talk stops an idle pawn by setting its path, animation and idle time directly (`relations.js:162`), past the `idle` verb; the dawn places pawns indoors by their door (`clock.js:37`); a death stops the pawn (`lifecycle.js:28`); and the verbs `goHome` and `idle` set fields themselves (`commands.js:40`, `45`). A pawn the player holds (VB-169) should change only by its commands and the rules every pawn has, through one module.

- [x] Operations in `sim/agents` for each: a pawn halted for a talk until a time, placed by its door, stilled at death; the verbs call agents' functions.
- [x] `node tools/writes.js --field agent.path` (and `phase`, `anim`, `inside`, `idleUntil`, `x`, `y`) lists only `sim/agents`, apart from seeding and the save codec.
- [x] Refactor rules of `BACKLOG.md`: behaviour unchanged, `tests/golden.json` unchanged, `npm run verify` passes.

Implementation review (6 November 2026):
- Impact: reads pawn liveness, agent activity and household/farm door coordinates; writes the existing
  movement fields only through `sim/agents`. No new module, saved state, random draw or growing loop.
- `haltForTalk` is a command so the earlier relations module reaches movement through the established
  deferred `issue` boundary. It preserves the original guard and `Math.max` deadline. Dawn's `placeByDoor`
  deliberately moves only coordinates, unlike `placeAtHome`, which resets activity.
- `stillAtDeath` preserves release-before-stop order; `goHome` sets its own phase; `idle` sets its deadline.
- What fell: nine writes past the movement owner across seven fields in four caller modules, and all
  seven movement entries in the ownership baseline. Direct movement-write coupling is removed from
  relations, commands, lifecycle and clock. Module load order and Sim's API remain unchanged.
- Cost: constant work per existing operation; a talk issues two bounded commands. No added entity pass.
- Command coverage checks pauses during work, homeward movement and indoor activity; a talk cannot shorten
  a pause. Invalid/missing deadlines and dead actors leave the state unchanged.
- Review of architecture/design: source modules build into one HTML page; simulation state is deterministic
  plain data with seeded system streams and owner checks. Presentation reads it and acts through commands.
  The five-layer architecture is a target, while the source still has deferred dependency cycles and
  outstanding ownership work (VB-174/175/178/179). The inhabited-pawn design particularly needs this movement
  boundary before VB-169; this change leaves the game's marriage, inheritance, food and custom rules intact.
- Upstream baseline investigated for VB-196, without implementation changes: one round on the published,
  stale-hash fixtures took 187.84 ms / 13,807 heir rankings / 390 candidate pairs on small-y40, and
  8,171.87 ms / 276,544 rankings / 12,928 pairs on medium-y60 (Node 24.22.1; diagnostic single calls).
  The medium fixture has 2,492 living pawns, beyond the roadmap's approximate 1,000-pawn reference.
  VB-196 remains ready for its separate cache and scheduling work.
- Screenshots: omitted because the refactor intentionally changes no visual design; real Chromium
  functionality checks are part of verification.
- Validation: `npm run verify` passed all 81 scripts (Node 24.22.1, system Chromium,
  `VB_TEST_JOBS=2 VB_SOFTWARE_RENDER=1 VB_CHROMIUM=/usr/bin/chromium`); golden states and work counters unchanged.
  `python3 build.py --check`, lint, owner audit and `git diff --check` pass. All four published fixtures
