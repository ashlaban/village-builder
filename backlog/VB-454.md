# VB-454: The width lint leaves out exports read only by a registry
Status: ready
Priority: 2
Size: S
Design ref: none (code structure). backlog/VB-415.md; backlog/VB-418.md, backlog/VB-228.md; docs/architecture/target-v2.md, principle 18
Goal: VB-415's lint counts every export of a module as interface. Some are not: a function exported only so that a registry can call it back (a job kind's `done` in `sim/kinds`, a calendar entry's `run` in `sim/clock`, a verb's body in `sim/commands`) is read by one module, which knows every domain by design, and no other domain can come to depend on it. Counting them made the lint ask for splits of modules far under 700 lines (`sim/fields` 420, `sim/meadows` 336: VB-434, VB-435), where a split adds a module and takes away no coupling. Leave them out of the count, so the width lint measures what it is for: how much of a module other domains can lean on.
Acceptance criteria:
- [ ] `tests/lint.js` names the registries in one list (`sim/kinds`, `sim/clock`, `sim/commands`; a module joins it only by this list, with its reason beside it). An export of another module that no module of `src/manifest.json` but a registry reads is not counted towards that module's width. The `sim` facade and the page do not count as readers, as today the facade is not counted. The readers come from the sources (`tools/writes.js` already lists each import), not from a hand-kept table.
- [ ] The lint prints, for a module over 15, both numbers: its exports and those left out, by registry, so the callbacks stay visible.
- [ ] `tests/width-baseline.json` is re-recorded with the new count; no module's number rises, and the PR lists each module's before and after. Expected by a grep on 15 November: `sim/fields` 28 to 18, `sim/meadows` 23 to 16, `sim/byre` 16 to 6 (off the baseline).
- [ ] A test in `tests/lint-rules.js`' suite on a small constructed case: an export read by a registry alone is left out; the same export read by a second module is counted.
- [ ] `AGENTS.md` (Conventions, the width line), `docs/gates.md` and `docs/architecture/modules.md` (Adding things) say so.
Notes / questions:
- 15 Nov 2026, from the review of the open refactors, decided by Kim in that session ("treat callbacks specially").
- Why. The width rule exists so that a module does not become something every domain leans on: each export is a name another module may come to depend on. A callback handed to a registry is not that. `hoed`, `weeded`, `binned` and `finishBreak` of `sim/fields` are named once, in the field kinds' records; `byreDay` and `shearing` once, in `CALENDAR`. The registry is central on purpose (it holds the order: `ASK`, the calendar's `ORDER`), so its knowing the name is no new coupling between domains. Counted as interface, these names made the lint open split tasks for modules of 336 and 420 lines, and a split there moves the names to a new module without removing one reader.
- Why not leave it to VB-418 and VB-228. They make the kinds' and verbs' callbacks private (the record is declared beside the function it calls), so the kinds' share of this goes away with them. The calendar's does not: `sim/clock` is a composition root and keeps its entries, since the order of a day is one decision; its callbacks stay exports for good. And until VB-418 lands, the lint would go on asking for splits.
- What it must not become: a way to hide width. The left-out names are printed, the list of registries is short and closed, and when an export gains a second reader it is counted again. A module does not join the list to get under 15.
- Order: beside VB-418; VB-434 and VB-435 wait for both.
- 15 Nov 2026 (Kim): priority 2, with the other three that unblock the rest of the refactors (VB-228, VB-418, VB-454, VB-455).
