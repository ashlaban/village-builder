# VB-197: The rules registry, with `death.hazard` as its first rule
Status: ready
Priority: 2
Size: M
Arch: yardstick
Phase: implement
Design ref: none (code structure). `docs/architecture/target-v2.md`, sections 2 (principle 11, rules combine contributions) and 4.1 (the rules registry); `docs/roadmap.md`, sections 3.0 and 5.3 (rule 6, compile what is hot).
Goal: Target-v2 makes the rules registry the kernel's one new piece. A rule is a quantity one domain owns; other domains contribute factors or terms to it, each declared with a range; a panel can explain it. Today's `deathRoll` (`sim/deaths`) is already one rule in small: a base hazard by age, times one plus hunger, times frailty, with one draw naming the cause. Build the registry with it as the first rule, behaviour unchanged. Then `value()` is measured from the start, and slice 1's `allowance` and later contributions (disease, traits, the urban hazard) have a door.
Acceptance criteria:
- [ ] A new module `sim/registry` in the kernel, under 200 lines, following the module conventions (VB-012, an `@sys` line, VB-013). It is listed in `src/manifest.json` after `sim/rules` and before `sim/deaths`.
  - `declare(spec)` and `contribute(c)` run at load only; a call after the first `Sim.seed` throws.
  - `value(st, rule, ctx)` returns the number; `explain(st, rule, ctx)` returns `{value, base, parts: [{key, source, label, cause, factor}]}`; `list()` returns the rules and their contributions.
  - `combine` is `product` or `sum`; `min` and `max` come when a rule needs them.
  - Specs and contributions take target-v2's shapes (4.1), cut to these fields. `compile` waits for its first consumer (`move.cost`, slice 10).
  - A contribution's `value` returns its factor; one that does not apply returns 1 (or 0 in a sum), so no list is built per call.
- [ ] `death.hazard`, owned by `sim/deaths`:
  - base `hazard(age) / YEAR_DAYS`;
  - contribution `hunger`: `1 + HUNGER.k(floor(age)) * hunger`, cause `hunger`, tunables `HUNGER.k`;
  - contribution `frailty`: the health factor, also cause `hunger`, as today's roll names it, tunables `HEALTH.riskBelow` and `HEALTH.riskSlope`;
  - the factors are multiplied in the order of today's expression, so the numbers are bit-identical.
  `deathRoll` asks `value` and names the cause as now (the base's cause by age if the draw falls under the base, `hunger` above it). Starvation at health 0 stays a check before the roll. One random draw per pawn-day, as now; `tests/deaths.js` passes unchanged.
- [ ] `tests/registry.js` in `npm test`:
  - `value` allocates nothing: 1,000,000 calls under `node --expose-gc` grow the heap by under 1 MB;
  - for 1,000 pawns of a populous state, `explain`'s value equals `value`, and its parts multiply to it;
  - a contribution declared after seeding throws.
- [ ] `tools/rules.js` prints every rule with its owner, combine, and its contributions (source, range, tunables). `--explain <pawn>` on a run or a save (`--load FILE`) explains one pawn's death hazard today.
- [ ] `VB.count.ruleValue` counts reads, if VB-192 is done; if VB-194 is done, the bench gains `Rules.value` in ns per call (otherwise VB-194 adds it).
- [ ] `tests/golden.json` unchanged: the registry is reached as `VB['sim/registry']`, not through `Sim`, so the API's hash stays. `npm run verify` passes.
- [ ] `CLAUDE.md`, Architecture: one line on the registry and how a module contributes to a rule.
Cost: one `value` per living pawn a day, about 1,000 calls at the late reference; under 0.1 ms a game day if a call stays under 100 ns. `explain` runs only in panels and tools.
