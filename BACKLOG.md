## How this backlog works

**Files and rows.** Each task has its own file, `backlog/VB-NNN.md`, which holds the full description and is the source of truth.
Its row here is the overview: when a task's name, arch, priority, size or what it waits for changes, update its row too; when its status
changes, move the row to that status's section. A new task takes the next free ID, gets a file and a row; the next free ID is above the task files of this checkout and of the branches pushed to origin in the last 14 days, so that sessions side by side do not take the same one (`tools/lib/ids.js`, VB-1680). A branch whose new IDs met main's renumbers them with `node tools/renumber.js --onto origin/main` before it merges main: only the IDs that met move, above every ID in sight, with the files named after them and every reference the branch made. IDs are never reused and the gaps are not filled: a task renumbered at a merge, because its ID met one on main, takes main's next free ID (the highest file on main, plus one), never a round number further on. Done tasks are moved, row unchanged, to `BACKLOG_ARCHIVE.md`;
their files stay in `backlog/`. Ready and Waiting for Kim are sorted by priority, then ID; Blocked by arch (in the order of the Archs table,
tasks outside every arch last), then priority, then ID; the archive by when a task was done, newest at the bottom.
`tests/backlog.js` checks that files and rows agree, and the order. `node tools/backlog.js` makes these moves from the task files
(`done`, `set`, `new`, `close-arch`, `sync`) and reads the backlog without these tables (`next`, `list`, `show`); `AGENTS.md`, Commands.

**Order and statuses.** Agents take only `Status: ready` tasks, in the Ready table's order: priority (1 first), then ID.
To change what runs first, change priorities; there is no other order. A task's `Touches:` line names the functions it will edit, so that tasks editing different ones run side by
side (VB-1677); how to write a task, that line included: [`docs/agents/tasks.md`](docs/agents/tasks.md).
A task is `ready` when its goal and acceptance criteria are stated; what it leaves open, its agent decides by `AGENTS.md`, Deciding without Kim.
`needs-review` tasks list the questions only Kim can answer (a Decided point moved, or a new thing the player can do); [`QUESTIONS.md`](QUESTIONS.md) gathers the open questions of all tasks
in one place, with proposed answers, and answered ones move to [`QUESTION_ARCHIVE.md`](QUESTION_ARCHIVE.md).
`needs-review` is for those questions only (Kim, 16 November; checked by `tests/backlog.js` since 25 November: each has its block in `QUESTIONS.md`): measurements and tuning do not generally block work. A task whose work is built and whose
hard checks pass is `done` though a measure was not taken or a target is out: leave the criterion unticked with its reason. Report the available measurements on the final PR or at nightly wrap-up. Small findings go to VB-663, up to ten per task. Record teleports and acts with no pawn in their respective open collectors for the slice wrap-up, and a module over the lint's line in the split collector (`node tools/backlog.js collect KIND`, `tools/lib/collect.js`). Give larger follow-up work its own task. Work not built, or waiting on another task, does not hold a task either: its criterion stays unticked naming the task that carries it, and the task is `done` (Kim, 25 November). A task noted by another, with its goal and criteria stated and no question, is `ready`; one that mends a red check is priority 1.
A `blocked` task has a `Waits for:` line after `Status:`, naming the open tasks it waits for, or `Kim`, separated by ", " (`Waits for: VB-185, VB-009`).
That line, not the prose of the goal or notes, is what holds it: when a task is done, the tasks that wait for it drop it, and a task left
waiting for nothing is set `ready` (the check fails until it is). A task taken over by a slice waits for the slice's plan, which confirms,
rewrites or closes it. Only blocked tasks have the line.

**Flags.** When a task finds that a decided number or reference no longer holds, or that its change moves a budget line it does
not own, it raises it in the same PR: a question in `QUESTIONS.md` or a new task, and a line at the top of its notes that begins `Flag:`.
A sentence deep in the notes is not enough. On 5 and 6 November the late fixture's 2,492 living (against about 1,000) and VB-174's
ledgers adding half to the save were written in task files, and no one acted on them until the review of 7 November.

**Causes.** A task that mends a defect names, in a `Cause: VB-NNN` line after `Status:`, the task whose change introduced it, where that is known (`tools/backlog.js set ID cause=VB-NNN`; VB-1619): the evaluation of independent review counts these.

**Archs and phases.** An arch groups the tasks that build one part of the design. Its tasks go through three phases:
- **plan:** a plan task makes the design concrete, deciding by `AGENTS.md`, Deciding without Kim, and asking Kim only what that leaves; it writes the arch's implement tasks with numbers and acceptance criteria, and sets them `ready`.
- **implement:** the tasks that build it, each small enough for one agent session (size S or M where possible).
- **wrap-up:** a task that checks the arch as a whole against the design with long runs and reports the numbers; it names the parameters a tuning run of Kim's would move, and tunes nothing. It is `blocked` until the arch's implement tasks are done.

Since 3 November 2026 the archs are the vertical slices of `docs/slices.md`, in the order Kim chose (slice 0 to slice 10). Each slice's plan task
is a design pass: it makes the slice's systems concrete, proposes its sections of `design.md` v0.4, and confirms, rewrites or closes the tasks
it took over from the earlier archs, which stay `blocked` until it has. A later slice's plan waits for the plan of the slice before it
(slices 1 and 2 run side by side); a slice's other tasks wait for its plan. The earlier archs are closed and kept in `BACKLOG_ARCHIVE.md` for their
done tasks; two, `ownership` and `animals`, still have open tasks that run beside the slices. A third arch beside them, `between` (11 November), holds the tasks of slice 2's plan VB-281.

A task file names its arch and phase in `Arch: <key>` and `Phase: plan|implement|wrap-up` lines after `Size:`; a task outside every arch
has neither, and its row shows `-` as its arch. The phase has no column: a plan task's name starts with "Plan:", a wrap-up's with "Wrap-up:",
and the check holds name and phase together. List an arch's tasks with `grep -l "^Arch: <key>" backlog/*.md`. A new arch gets a row in the Archs table;
an arch with no open tasks left moves to the archive's closed archs.

**Design refs** point to sections of `design.md` ("Village builder: game design snapshot v0.4"). Refs written before 3 November point to
v0.3's sections (`docs/design-v0.3.md`); v0.4 keeps v0.3's subsection names, so most still find their place (v0.4's Status of this snapshot
says where each section went).

**Refactor rules** (every task titled "Refactor:"):
- Behaviour may change where that makes the separation of responsibilities clearer (Kim, 18 November): the task names each change of behaviour in a line of its result, and the hard checks pass. A refactor that claims none shows it: `node tools/same.js --base REF` prints `same` against the commit the task started from (`docs/testing.md`), and its line is in the PR.
- A move and a change are separate commits: code that only moves does so verbatim apart from the module wrapper, the dependency lines at its top and its return list; a rename is not part of a move (below). Moved code is formatted by Prettier (`npm run format`), as all of `src/` is.
- Renames (Kim, 15 November: naming is very important): a name that misleads is renamed, whether a module, a function, a state field or a name of the `Sim`, `ArchGen` and `Culture` APIs. A rename is a commit of its own, apart from any move, so each diff is either a move or a rename. It changes every use: `src/`, `tests/`, `tools/`, `AGENTS.md`, `docs/architecture/` and the open task files, so their references and greps stay valid; done tasks and the archives keep the old name, as history. The PR lists each old and new name. A renamed function or module shows `same` like any move. A renamed state field or saved key changes the state itself, so `tools/same.js` cannot show it: it is a task of its own, whose PR names the leaves that differ, shows that no others do, and says what happens to an old save.
- A new module follows the VB-012 convention, starts with an `@sys` header (VB-013), is listed in `src/manifest.json` after every module it reads. Its length is not capped: over 700 formatted lines (the 400 of the packed sources, rescaled when `src/` was formatted, 13 November) the lint asks for an open line naming it in the split collector, "Refactor: module splits, collected" (size L; Kim, 25 November), split by concern; the task that takes it there adds the line with `node tools/backlog.js collect split where=<key> what=... from=<its ID>` (VB-413, VB-414). A session takes one line of the collector, names the module's responsibilities and where each belongs before any code moves, splits by them and ticks the line; the collector stays open until every line is ticked.

**Testing, work counters and cost growth:** permanent golden baselines are retired (VB-408). Older tasks that require a golden
check or update instead follow `docs/testing.md`; preserve behavior for refactors, test the intended contracts for behavior changes.
A work-counter baseline change is reported in its PR. Counters and cost growth are targets: they report their residual and never fail, and a change does not raise
a target to hide one (Kim, VB-261). A criterion worded as a line ("at most 30 ms", "verify passes") means: moved towards the target, its
residual reported, and who closes what is left named; "verify passes" means its hard checks pass. The commands and limits are in
`AGENTS.md` (Commands and Taking a task).
